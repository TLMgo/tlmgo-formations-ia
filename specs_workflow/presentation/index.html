Présentation · 30 minutes

Comment des SPECS peuvent m'aider
et aider mon agent

Dans la Planification, dans le Coding, dans les Tests et dans les Reviews.

quatre étapes · à chaque étape, une seule question : en quoi la spec aide ici ?
Le point de départ

Ce qui se passe sans spec

Le vrai risque n'est pas que l'agent soit lent. C'est qu'il produise du code qui a l'air juste et résout tranquillement le mauvais problème.

Planification

Le besoin reste dans le chat. On se met d'accord à l'oral, et chacun repart avec une version un peu différente.

Coding

L'agent code vite. Donc il code vite dans une direction que personne n'a vraiment choisie.

Tests

Les tests sont écrits après, en regardant le code. Ils confirment ce que le code fait déjà.

Reviews

Beaucoup de code qui a l'air correct. On approuve « parce que ça semble raisonnable ».

L'exemple qui servira partout

Une spec = des exigences,
chacune avec ses scénarios

Une spec empile des exigences. Chaque exigence a plusieurs scénarios — ce qu'on appelle les cas. Notre login : 3 exigences, 13 scénarios, et ce n'est pas fini.

Plusieurs scénarios décrivent un refus, une limite ou une contrainte de sécurité, pas un succès. C'est là que se cachent les vrais bugs.

### Exigence : Connexion
Même refus pour un email inconnu ou un mauvais mot de passe
(ne pas révéler quels comptes existent).
  scénarios :
  Cas 1  Identifiants valides       → connexion acceptée
  Cas 2  Email inconnu / mdp faux   → même message d'erreur
  Cas 3  Compte désactivé           → refusé
  Cas 4  Champ vide                 → erreur de saisie
  Cas 5  Email en MAJUSCULES        → accepté
  Cas 6  Déjà connecté              → redirigé

### Exigence : Blocage après trop d'essais
Bloquer après 5 échecs, comptés par compte ET par IP.
  scénarios :
  Cas 7  5 échecs / 15 min          → bloqué 30 min + message
  Cas 8  échecs de plusieurs IP     → bloqué quand même (par compte)
  Cas 9  une IP, 20 comptes         → cette IP bloquée (par IP)
  Cas 10 succès                     → compteur remis à zéro
  Cas 11 bon mdp pendant le blocage → refusé
  Cas 12 après 30 min               → connexion possible

### Exigence : Journalisation
Tout journaliser, jamais le mot de passe.
  scénarios :
  Cas 13 date, email, IP, résultat  → jamais le mot de passe

  … et d'autres exigences (mdp expiré, e-mail non vérifié…)
Le fil conducteur

Les mêmes specs servent quatre fois

Un changement s'écrit dans des documents simples — le pourquoi, la conception, les tâches, les cas. Les mêmes documents sont relus à quatre étapes, et à chaque fois ils rendent un service différent.

01

Planification

En quoi la spec aide ?

Se mettre d'accord avant d'écrire le code.

Pour moi je traite les questions avant de coder, quand corriger ne coûte qu'une lignePour l'agent il reçoit des cas clairs et une liste de fichiers, pas une conversation à deviner
Planification

Les questions sortent maintenant,
pas en production

Écrire les cas oblige à se poser des questions qu'on n'aurait pas posées spontanément. Répondre coûte une ligne aujourd'hui, un incident plus tard.

La question sort en écrivantCe qu'elle coûte si elle ne sort pas
« Et si l'email n'existe pas ? »On peut deviner quels comptes existent
« On compte les échecs par IP ou par compte ? »Par IP seule : contournée par une attaque venant de mille IP. Par compte seul : un attaquant verrouille les comptes des autres. → il faut les deux.
« Et les majuscules dans l'email ? »Un ticket support par semaine, pendant deux ans
« Garde-t-on une trace des tentatives ? »Impossible d'enquêter après un incident

Les questions qu'on ne se pose pas en écrivant la spec, on se les pose en production.

Planification

Chaque question tranchée
devient une décision écrite

Les questions d'avant appellent des réponses. La spec garde ces décisions et leur logique — pas seulement le choix, mais le pourquoi. Six mois plus tard, on ne re-débat pas : c'est écrit.

Rien ne part au code tant que chaque question n'a pas sa décision écrite. Sinon, c'est l'agent qui tranchera à ta place — au hasard.

## Question tranchée → décision
« On compte les échecs par IP ou par compte ? »

## Décision
- On compte par compte ET par IP.
  Pourquoi : par IP seule, une attaque distribuée passe ;
  par compte seul, on peut bloquer les comptes des autres.
- Blocage 30 min, pas définitif.
  Pourquoi : ne pas appeler le support à chaque oubli.
Planification

Le client peut la lire
et décider lui-même

Une spec, c'est du texte : ce que le système doit faire, écrit en clair. Pas de code, pas de terme technique. Le client peut la lire et trancher. C'est une possibilité, pas une obligation : beaucoup d'équipes ne le font pas, et la spec reste tout aussi utile en interne.

S'il veut décider

« Après combien d'essais on bloque le compte ? » — une question en français, une réponse en français, écrite dans la spec.

S'il veut valider

Il approuve une liste de cas, pas des lignes de code. Ce qu'il lit est exactement ce qui sera testé.

S'il ne veut pas

Rien ne change pour l'équipe. La spec sert d'abord au dev et à l'agent ; le client est un bonus.

# Ce que le client ne lira jamais
if not user or not verify(pw, user.hash):
    raise HTTPException(401, "invalid_credentials")
if not user.active:
    raise HTTPException(401, "invalid_credentials")
## Ce que le client peut lire — et valider

QUAND quelqu'un se trompe d'email ou de mot de passe
ALORS le message d'erreur est exactement le même
   — pour qu'on ne puisse pas deviner les comptes qui existent.

QUAND un compte a été désactivé
ALORS il ne peut plus se connecter.
Planification

Elle rend la découpe
vérifiable

La liste des tâches, c'est le planning lui-même — la spec ne la fait pas à ta place. Ce qu'elle apporte : chaque tâche pointe vers un cas, donc on vérifie que rien ne manque et que rien n'est en trop.

Se repère seul

Une tâche qui ne sert aucun cas = du travail que personne n'a demandé.

Se repère seul

Un cas servi par aucune tâche = un oubli, visible avant même de coder.

Effet important

Le test est une tâche, au même niveau que le code. Fini le « on testera si on a le temps ».

## Tâches

- [x] A.1 Écran de connexion                → Cas 1, 2
- [ ] A.2 Refuser un compte désactivé       → Cas 3
- [ ] A.3 Rediriger un utilisateur connecté → Cas 6
- [ ] B.1 Bloquer 5 échecs + reset au succès → Cas 7, 10, 12
- [ ] B.2 Compter par compte ET par IP      → Cas 8, 9
- [ ] J.1 Journaliser chaque tentative      → Cas 13
02

Coding

En quoi la spec aide ?

Donner à l'agent un cadre écrit, pas une conversation.

Pour moi je ne ré-explique plus à chaque fois, et je peux lancer plusieurs tâches en même tempsPour l'agent il relit le même texte à chaque session, et sait où s'arrêter
Coding

L'agent relit le contexte,
au lieu de s'en souvenir

Contexte dans le chat

Session fermée = contexte perdu. Discussion trop longue = contexte coupé. Nouvelle session = on ré-explique.

Contexte dans les fichiers

L'agent lit la spec au démarrage. Même point de départ à chaque session, quelle que soit la machine ou le modèle.

Le gain est discret, et c'est le plus rentable : reprendre après une coupure ne demande plus aucune ré-explication.

Coding

Elle attrape trois dérives
que rien d'autre ne voit

Trois erreurs classiques d'un agent qui code vite. Aucune ne se voit dans du code d'apparence propre. Toutes se voient face à la spec.

Le travail en trop

L'agent ajoute une fonction, une option que personne n'a demandée. Le code est bon — il n'était pas demandé.

Attrapé par : le fichier ajouté n'est pas dans la liste prévue.

La valeur inventée

Une donnée manque, l'agent met une valeur « raisonnable ». Ça marche, ça passe la revue, personne ne le voit pendant un an.

Attrapé par : une consigne écrite — jamais de valeur inventée quand une donnée manque.

Le travail à moitié fait

Le cas qui marche est codé, la démo passe. Le compte désactivé, jamais fait.

Attrapé par : le Cas 3 est une tâche cochée ou non — pas un détail découvert en prod.

Coding

Elle permet d'utiliser
un modèle moins cher pour coder

Un gros modèle coûte cher parce qu'il doit deviner ce qu'on veut. Quand une tâche est déjà bien décrite, il n'y a plus rien à deviner : un modèle plus léger suffit.

Réfléchir — gros modèle (ex. Opus)

Là où il faut du jugement : explorer le code, poser les bonnes questions, écrire les cas, découper en tâches.

Exécuter — modèle léger (ex. Sonnet)

Là où tout est déjà écrit : la tâche, ses fichiers, son test. Il applique, il ne décide pas. Plusieurs fois moins cher, sans perte.

Sans spec, on paie le gros modèle à chaque ligne pour qu'il redevine l'intention. Avec spec, on le paie une seule fois : pour l'écrire.

## Tâche A.2 — assez décrite pour un modèle léger
Cas       : Cas 3 — un compte désactivé
            ne peut plus se connecter
Fichiers  : vérification du login,
            test de la connexion
Test      : « compte désactivé → refusé »
Ne pas toucher : le message d'erreur,
            ni les autres cas de la spec
03

Tests

En quoi la spec aide ?

Tester ce qu'on a promis, pas ce que le code fait.

Pour moi je vois ce qui est garanti et ce qui ne l'est pas, sans lire le codePour l'agent il écrit les tests à partir des cas, sans regarder l'implémentation
Tests

On teste que les cas marchent. Pas que le code marche.

# écrit en regardant le code
def test_verifie_mot_de_passe():
    user = compte(mot_de_passe="secret")
    assert verifie(user, "faux") is False
# → recopie la fonction. Renomme-la : le test
#   casse. Le comportement, lui, n'a pas bougé.
# écrit à partir du Cas 2, sans ouvrir le code
def test_meme_erreur_email_ou_mdp_faux():
    r1 = login(email="inconnu@x.io", mdp="x")
    r2 = login(email="connu@x.io", mdp="faux")
    assert r1.erreur == r2.erreur
# → réécris tout le code : ce test ne bouge pas.
Tests · le point d'attention

Attention : qui écrit le cas,
et qui écrit le test ?

Si le même agent, dans la même session, écrit le cas, puis le code, puis le test, il peut répéter la même erreur dans les trois. Les tests passent au vert, mais ils ne vérifient rien de neuf.

Sans ces trois conditions, le test n'est pas un contrôle indépendant : c'est la même erreur écrite trois fois.

Condition 1

Le cas a été écrit ou relu par un humain. C'est là qu'est le vrai choix, et il ne se délègue pas.

Condition 2

Le test est écrit dans une autre session, ou par un autre agent, avec le cas seul sous les yeux.

Condition 3

Le test ne parle que de ce qu'on voit de l'extérieur : ce qui entre, ce qui sort, le message d'erreur. Rien du code interne.

Tests

Elle te dit quoi tester,
les refus compris

L'avantage : la liste des cas est déjà la liste de ce qu'il faut vérifier. Sans elle, on teste le cas qui marche et on oublie les refus et les limites — là où sont les bugs.

Le piège le plus courant : on ne teste que le cas qui marche — alors que la spec passe l'essentiel de son temps à décrire ce qui doit être refusé.

Ça marche

Le cas normal.
Bons identifiants → connexion

C'est refusé

Ce qui doit être bloqué.
Email inconnu, mot de passe faux, compte désactivé

Les bords

Les limites exactes.
Champ vide → erreur. Majuscules → accepté

L'ancien état

Les données déjà en place.
Un vieux compte se comporte toujours bien

Tests

Et elle montre
lequel n'a pas encore de test

Une fois les tests écrits, la spec sert de liste de contrôle : chaque cas est vérifié, ou pas. Le trou saute aux yeux — sans logiciel spécial, une simple recherche suffit.

« Le Cas 3 n'a pas de test » se comprend par tout le monde. Un « 92 % du code testé », non.

04

Reviews

En quoi la spec aide ?

Relire contre un contrat clair, pas contre une impression.

Pour moi je relis d'abord la spec, puis le code en face — et je peux refuser sur des faitsPour l'agent il fait le premier tri : quel cas n'a pas de test ?
Reviews · l'argument principal

Elle rend la review
rapide et fiable

Sans spec, on relit du code à l'instinct et on approuve « parce que ça a l'air correct ». C'est une impression, pas une review.

Avec la spec, on a un repère court à comparer au code — plus rapide, et partagé par toute l'équipe.

On lit la spec comme référence, puis on vérifie le code en face. Jamais tout le code sans repère.

Reviews · l'exemple concret

Une bonne PR, reliée à la spec

Voici à quoi ressemble une Pull Request qui s'appuie sur la spec. Tout ce qu'il faut vérifier est déjà là, écrit.

Le relecteur ne devine rien : il compare la PR à la spec. Vert partout = conforme à ce qui avait été promis.

Reviews

La revue tient
en quatre questions simples

  • La PR dit-elle quels cas elle traite ?
    Sans référence, personne ne peut vérifier quoi que ce soit.
  • Les fichiers modifiés étaient-ils dans la liste prévue ?
    Un fichier en plus, c'est du travail non demandé ou un effet de bord.
  • Chaque cas touché a-t-il au moins un test ?
    Vérifiable automatiquement dès que les tests portent le numéro du cas.
  • Spec changée → code et tests changés dans la même PR ?
    Sinon la spec et le code commencent à se contredire, à partir d'ici.
Fichiers prévus              Fichiers changés
écran de connexion           écran de connexion
vérif. mot de passe          vérif. mot de passe
test de la connexion         test de la connexion
                             un fichier ajouté en plus
                             ← pas dans la liste prévue

En cas de désaccord, la spec gagne, ou on la corrige dans la même PR. Jamais « on verra plus tard ».

Reviews

Elle donne le droit de refuser

Sans référence, refuser une PR revient à opposer son goût à du code qui marche : épuisant, subjectif, on finit par céder. Avec la spec, on refuse sur des faits — et la spec, c'est les cas, les décisions, le périmètre et les contraintes.

La spec transforme un débat de personnes en simple vérification. C'est ce qui rend la revue tenable quand le volume de code explose.

Un cas

« Le Cas 3 n'a aucun test » — un fait, pas une opinion.

Une décision

« La spec décide : compter par compte ET par IP ; le code ne compte que par IP » — un fait.

Le périmètre

« Ce fichier n'était pas dans la liste prévue » — un fait.

Une contrainte

« La spec dit : ne jamais inventer de valeur ; le code en invente une » — un fait.

Reviews

Elle donne à l'agent
un premier tri utile

Ces questions sont simples et répétitives. Elles ne demandent aucun goût, juste une comparaison avec un texte — donc l'agent les fait bien, et vite.

L'agent fait ce tri en quelques secondes. On vérifie sa réponse — il peut se tromper. Mais sans spec, la question ne pourrait même pas se poser.

À retenir

Quatre étapes,
les mêmes specs

  • Planification — la spec fait sortir les questions tôt et garde les décisions et leur raison, pour ne pas les reprendre dans six mois.
  • Coding — elle donne à l'agent un cadre écrit qu'il relit à chaque session.
  • Tests — on teste que les cas marchent, pas que le code marche.
  • Reviews — on relit la spec avant le code, et on refuse sur des faits.

Le code, les tests et la review s'appuient tous sur la même spec — des documents texte, rangés avec le code, aucun outil à installer.

Une spec, ce n'est pas de la doc en plus. C'est ce qui aide l'équipe et l'agent à construire la bonne chose.

Pour finir

Efface le code,
garde les specs

Si les specs sont bien faites, on peut supprimer tout le code de l'appli et la recréer à l'identique, avec les mêmes fonctionnalités, à partir des seules specs.

  • Avec l'IA, le code est devenu bon marché.
  • Les specs comptent autant, sinon plus que le code.
  • Le code seul ne dit pas pourquoi il fait ça — la spec, oui.
  • On change tout le code lors d'une refonte ; les specs, elles, restent.
